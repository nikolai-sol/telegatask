# Менеджерский SEO-отчёт: дизайн

**Дата:** 2026-09-01

**Первый отчёт для обновления:** `https://flowerlife-school.com/`

**Язык отчёта:** русский (`ru`)

## Контекст

Текущий HTML-отчёт начинается с технических находок и таблиц по страницам. Он полезен SEO-специалисту, но не отвечает на первые вопросы руководителя: каково общее состояние сайта, что мешает росту, где сайт находится по основным запросам, виден ли он в ответах Алисы и что делать сначала.

Часть интерфейса и рекомендаций выводится на английском, хотя запуск выполнен с `language=ru`. В отчёт также попали внутренние термины: `Normalized evidence files`, `Source coverage`, коды проверок и служебные статусы. Они занимают место и требуют дополнительного объяснения.

## Цель

Перестроить HTML-отчёт для руководителя:

1. Сначала показать оценку сайта, основные проблемы, позиции, видимость в ответах Алисы и скорость.
2. Сгруппировать одинаковые проблемы и объяснить их влияние простым русским языком.
3. Спрятать подробности по URL и методику в раскрывающиеся блоки.
4. Сохранить подробный JSON и исходные файлы проверки для специалиста, не вынося их в основную часть отчёта.
5. Применить новую структуру не только к Flowerlife, но и ко всем будущим запускам команды SEO-отчёта.

## Выбранный вариант

Один HTML-отчёт с двумя уровнями чтения:

- открытая менеджерская часть;
- закрытые по умолчанию технические блоки.

Отдельный краткий файл не создаётся, чтобы данные и формулировки не расходились. Переключатель режимов также не нужен: стандартные HTML-блоки `details` и `summary` работают без JavaScript и остаются доступными с клавиатуры.

- рынок и поисковую систему;
- короткую отметку о полноте данных.

Технические идентификаторы запуска и ISO-время в основной части не показываются.

### 2. Общая оценка

Первый экран содержит:

- общий SEO-скоринг и словесный статус при достаточной полноте либо состояние «Предварительная оценка» / «Недостаточно данных» по правилам ниже;
- четыре составляющие с коротким пояснением;

Диапазоны статуса:

| Балл | Статус |
| --- | --- |
| 0-39 | Критическое состояние |
| 40-59 | Высокий риск |
| 60-79 | Требуются улучшения |
| 80-100 | Хорошее состояние |

### 3. Что мешает росту

Показываются до пяти подтверждённых сгруппированных проблем. Если проблем меньше, отчёт выводит фактическое число. Повторяющаяся проблема не выводится отдельной строкой для каждого URL.

Каждая карточка содержит:

- понятное название;
- приоритет;
- сколько страниц затронуто;
- почему это важно для сайта;
- что сделать;
- ссылку на соответствующие страницы в закрытом разделе.

Проблемы группируются по коду проверки. Нормализованная группа хранит `scope`, `affectedUrls[]`, максимальный приоритет и локализованное представление. URL берутся из структурированных полей находок и crawl-данных, но не извлекаются из текста доказательства. Для проблемы уровня сайта отчёт пишет «Проблема уровня сайта» и ведёт в соответствующий технический блок. Для проблемы страниц показывается число уникальных URL из проверенной выборки. Технические коды вроде `missing_canonical` в менеджерской части не показываются.

Показываются:

### 6. Скорость и удобство

Показываются средние оценки отдельно для мобильных устройств и компьютеров, страница с самой низкой оценкой производительности на мобильном устройстве и выявленные факторы замедления. Фактор можно назвать главным только тогда, когда Lighthouse возвращает сопоставимую численную оценку его влияния. Рядом явно указано, что Lighthouse моделирует загрузку в лабораторных условиях и не заменяет данные реальных посетителей.

Основная таблица не содержит полный список аудитов Lighthouse. Подробности входят в карточки страниц.

### 7. Что делать сначала

Краткий список из трёх этапов:

1. Устранить блокирующие проблемы.
2. Исправить проблемы, влияющие на видимость и посадочные страницы.
3. Улучшить скорость, контент и дополнительные сигналы.

В каждом этапе показывается результат, который можно проверить. Этап формируется только при наличии соответствующих подтверждённых проблем. Пустые этапы не выводятся. Полный технический backlog в основной части не показывается.

## Формула скоринга

Общая оценка рассчитывается только из измеренных составляющих:

| Составляющая | Вес |
| --- | ---: |
| Техническое SEO и индексируемость | 40% |
| Позиции в Яндексе | 25% |
| Скорость и удобство | 20% |
| Видимость в ответах Алисы | 15% |

Для каждого компонента рассчитываются два показателя:

- `collectionCoverage`: какая доля запрошенных данных фактически получена;
- `scoringCoverage`: какая доля может участвовать в скоринге после проверки минимальной выборки и обязательных полей.

Если компонент не проходит минимальную выборку, его `scoringCoverage` равно нулю, даже когда все один или два заданных запроса успешно выполнены. Эффективный вес компонента равен `номинальный вес × scoringCoverage`.

Для компонентов с положительным эффективным весом предварительный балл рассчитывается так:

```text
сумма(балл компонента × эффективный вес) / сумма эффективных весов
```

Полнота расчёта равна сумме эффективных весов. Покрытие позиций и ответов Алисы равно доле успешно проверенных запросов. Покрытие Lighthouse считается по полным успешным парам mobile и desktop. Покрытие технического SEO учитывает завершённость обхода и применимость атомарных правил. В отчёте дополнительно показываются понятные счётчики сбора: например, «5 из 5 запросов» и «6 из 6 пар страниц».

Правила вывода общей оценки:

- полнота 80-100%: показываются балл и статус;
- полнота 60-79%: показывается «Предварительная оценка» без уверенного статуса состояния сайта;
- полнота ниже 60%: общий балл не показывается, вместо него выводится «Недостаточно данных».

Если составляющая не измерена из-за отсутствия необязательного источника, формула автоматически распределяет её вес между компонентами с положительным эффективным весом только для математического расчёта предварительного балла. Полнота всегда остаётся видимой и не нормализуется. Отсутствие доступа к Яндекс.Вебмастеру или Google Search Console само по себе не считается ошибкой сайта и не входит в покрытие четырёх используемых составляющих.

### Техническое SEO и индексируемость

Оценка состоит из проверяемых групп:

| Группа | Баллы |
| --- | ---: |
| HTTP-ответы и отсутствие блокировки индексации | 45 |
| `robots.txt` и sitemap | 15 |
| Canonical и отсутствие конфликтов | 15 |
| Title, description и H1 | 15 |
| Внутренние ссылки и редиректы | 10 |

Атомарные правила технической оценки:

- 20 баллов: доля проверенных HTML-страниц с успешным 2xx-ответом;
- 25 баллов: доля страниц, предназначенных для индексации, без `noindex`, блокирующего `X-Robots-Tag` и конфликтующих robots-сигналов;
- 5 баллов: `robots.txt` не блокирует главную страницу и проверяемые контентные разделы;
- 10 баллов: XML sitemap доступен, корректно разбирается и содержит URL сайта;
- 12 баллов: доля индексируемых страниц с корректным canonical;
- 3 балла: доля страниц без конфликтующих canonical, robots и hreflang-сигналов;
- 5 баллов: title, из них 3 за наличие и 2 за отсутствие дубля;
- 5 баллов: description, из них 3 за наличие и 2 за отсутствие дубля;
- 5 баллов: наличие H1;
- 5 баллов: отсутствие битых внутренних целей;
- 3 балла: отсутствие многошаговых редиректов;
- 2 балла: отсутствие страниц без входящих ссылок внутри наблюдаемого графа, кроме главной.

Alt-тексты и структурированные данные показываются как отдельная диагностика, но не входят в общий балл. Текущий обход не отличает декоративное изображение с пустым `alt` от изображения, которому текст действительно нужен, а schema применима не ко всем страницам.

Страницами, предназначенными для индексации, по умолчанию считаются успешно загруженные публичные HTML-страницы, прошедшие действующие исключения обходчика для аккаунта, авторизации, регистрации и служебных действий. Главная страница всегда входит в эту группу. В будущем явная настройка назначения URL имеет приоритет над этим правилом.

Проверка, которая неприменима к странице, исключается из знаменателя своей группы. Ошибка сбора уменьшает полноту данных, но не снижает балл. Итог и составляющие округляются до целого числа стандартным математическим округлением.

Crawler сохраняет структурированную статистику `attemptedUrlCount`, `eligibleDiscoveredCount`, `droppedEligibleCount` и `truncated`. `eligibleDiscoveredCount` включает каждый уникальный допустимый same-origin URL, обнаруженный в seed, sitemap или внутренних ссылках до применения лимита очереди. Отброшенный из-за лимита URL учитывается в `eligibleDiscoveredCount` и `droppedEligibleCount`, даже если не попал в прежний массив `discoveredUrls`.

Завершённость обхода равна `attemptedUrlCount / eligibleDiscoveredCount` и ограничивается диапазоном от 0 до 1. При нулевом знаменателе завершённость равна нулю. Старого `discoveredUrls` недостаточно для этой формулы, поэтому новая структурированная статистика обязательна.

Для каждого атомарного правила `i` рассчитываются:

```text
ruleCoverageᵢ = measuredCountᵢ / applicableCountᵢ
passRateᵢ = passedCountᵢ / measuredCountᵢ
technicalScore =
  Σ(weightᵢ × ruleCoverageᵢ × passRateᵢ)
  / Σ(weightᵢ × ruleCoverageᵢ)
  × 100
```

Правило с нулевым `applicableCount` исключается из обеих сумм. Правило с нулевым `measuredCount` имеет нулевое покрытие и не получает ни ноль, ни полный балл. Для правила уровня сайта counts равны 1 или 0. Для правила по страницам они считаются по применимым URL. Пустое значение, полученное при успешном разборе страницы, считается измеренным отсутствием; поле, потерянное из-за ошибки сбора, считается неизмеренным.

Покрытие атомарных правил рассчитывается отдельно:

```text
atomicRuleCoverage =
  Σ(weightᵢ × ruleCoverageᵢ)
  / Σ(weightᵢ для применимых правил)
```

`collectionCoverage` технической составляющей равно `завершённость обхода × atomicRuleCoverage`. Техническое `scoringCoverage` равно `collectionCoverage`, если главная страница успешно разобрана как HTML; иначе оно равно нулю. Поэтому полностью заполненная, но усечённая выборка не может считаться стопроцентным техническим покрытием.

Если главная страница или более половины предназначенных для индексации страниц закрыты от индексации, итоговая оценка не может быть выше 39. Это не позволяет хорошей скорости скрыть критическую проблему видимости.

### Позиции в Яндексе

Каждый успешно проверенный основной запрос получает балл:

| Позиция | Балл |
| --- | ---: |
| 1-3 | 100 |
| 4-10 | 80 |
| 11-20 | 60 |
| Не найден среди первых 20 результатов | 0 |

Оценка равна среднему по проверенным запросам. `collectionCoverage` равно числу успешно проверенных запросов, делённому на число заданных. `scoringCoverage` равно `collectionCoverage`, если успешно проверены минимум три запроса и не менее 60% заданной выборки; иначе оно равно нулю. При меньшей выборке отчёт показывает позиции как наблюдение без отдельного скоринга. Запросы с технической ошибкой исключаются из расчёта и уменьшают полноту данных. Глубина проверки сохраняется рядом с результатом, чтобы отсутствие сайта не трактовалось шире фактически просмотренной выдачи. При отсутствии заданных запросов оба покрытия равны нулю.

### Скорость и удобство

Оценка использует только полные успешные пары Lighthouse для одного URL. Полная пара содержит численные performance, accessibility и best-practices в обоих профилях mobile и desktop. Профиль с ошибкой или отсутствующей обязательной категорией не подставляет ноль: вся пара исключается и уменьшает покрытие.

Формула компонента:

- 50%: среднее performance мобильных профилей из полных пар;
- 20%: среднее performance компьютерных профилей из полных пар;
- 20%: среднее accessibility по обоим профилям всех полных пар;
- 10%: среднее best-practices по обоим профилям всех полных пар.

`collectionCoverage` равно числу полных пар, делённому на число запрошенных пар. `scoringCoverage` равно `collectionCoverage`, если есть хотя бы одна полная пара; иначе оно равно нулю. Если пары не запрашивались, оба покрытия равны нулю. При равной самой низкой мобильной performance оценке худшая страница выбирается по URL в алфавитном порядке.

Категория Lighthouse SEO не входит сюда, чтобы не считать техническое SEO дважды.

### Видимость в ответах Алисы

Оценка равна доле выбранных запросов, в ответах на которые сайт был использован как источник:

```text
использования сайта / успешно проверенные запросы × 100
```

`collectionCoverage` равно числу успешно проверенных запросов, делённому на число заданных. `scoringCoverage` равно `collectionCoverage`, если успешно проверены минимум три запроса и не менее 60% заданной выборки; иначе оно равно нулю. Если знаменатель равен нулю или выборка меньше минимума, показывается только наблюдаемый результат без скоринга. При отсутствии заданных запросов оба покрытия равны нулю. Появление домена среди найденных ссылок можно показывать отдельно, но оно не заменяет использование сайта как источника ответа.

### Оценка страницы

Оценка URL использует только данные, применимые к этой странице:

- индексируемость: 45 баллов, из них 20 за успешный HTTP-ответ и 25 за отсутствие блокирующих директив;
- содержание страницы: 30 баллов, из них 8 за title, 7 за description, 7 за H1 и 8 за canonical;
- внутренняя структура: 10 баллов, из них 5 за входящие внутренние ссылки и 5 за отсутствие битых исходящих внутренних ссылок;
- Lighthouse: 15 баллов по формуле `10 × mobilePerformance / 100 + 5 × desktopPerformance / 100`, если оба профиля завершились успешно и вернули численный performance.

Для title и description балл делится поровну между наличием и отсутствием дубля. Проверка без применимых данных исключается, а её вес распределяется между измеренными группами страницы. Если полной Lighthouse-пары для URL нет, её вес также распределяется между тремя измеренными группами, а скорость помечается как неизмеренная. Отсутствующий численный показатель уменьшает покрытие и никогда не считается нулём или полным баллом. Страница, предназначенная для индексации, но закрытая директивой `noindex`, не может получить больше 39 баллов.

## Язык и стиль

При `language=ru` весь интерфейс HTML и все менеджерские выводы формируются на русском. Это включает заголовки, статусы, названия проблем, действия, подписи таблиц, пустые состояния, ограничения и даты.

Для HTML используется отдельная presentation-модель:

- словарь всех статических подписей и состояний источников;
- русские названия приоритетов: «критический», «высокий», «средний», «низкий»;
- русские шаблоны названия, влияния и действия для каждого поддерживаемого кода находки;
- русские названия категорий Lighthouse и понятные названия известных диагностик;
- форматирование дат, чисел и пустых значений для выбранной локали.

Английские поля `evidence`, `action` и сообщения источников из сырого JSON не вставляются напрямую в менеджерскую часть. Неизвестный код находки не показывается руководителю и остаётся в закрытых данных для специалиста. Новая находка считается готовой для менеджерского отчёта только после добавления локализованного представления.

Допустимы только официальные названия сервисов и метрик: Яндекс, Яндекс.Вебмастер, Google Search Console, Lighthouse, LCP, CLS и аналогичные обозначения.

Правила текста:

- короткие предложения;
- одна мысль в абзаце;
- сначала факт, затем влияние и действие;
- без повторения одинаковых оговорок в нескольких разделах;
- без рекламных формулировок и общих обещаний;
- без внутренних терминов, кодов и английских служебных статусов;
- без выводов, которые не подтверждаются собранными данными.

Для других языков сохраняется словарь интерфейса. Неизвестный язык не должен приводить к смеси русского и английского: используется явно выбранный запасной язык.

## Публикация

Для принятого отчёта `flowerlife-school.com` согласован публичный GitHub Pages канал текущего репозитория.

- исходный проверенный bundle остаётся в timestamped-каталоге `reports/`;
- публичная копия размещается в `mini-app/seo-reports/flowerlife-school/`;
- `report.html` публикуется как `index.html` для короткого адреса;
- HTML содержит `meta robots="noindex,nofollow"`, чтобы публичная ссылка не предназначалась для поисковой индексации;
- рядом публикуются `report.json` и каталог `evidence/`, чтобы относительные ссылки не ломались;
- целевой адрес: `https://nikolai-sol.github.io/telegatask/seo-reports/flowerlife-school/`;
- workflow `.github/workflows/deploy-miniapp.yml` запускается push в `main` при изменении `mini-app/**`;
- после workflow проверяются HTTP 200 для `index.html`, `report.json` и каждой ссылки на evidence из HTML.

Публикация выполняется только после локальной проверки нового отчёта и не включает `execution-plan.md`. GitHub Pages не имеет авторизации, поэтому опубликованный отчёт доступен всем, у кого есть ссылка. Пользователь явно подтвердил публичную публикацию этого отчёта 2026-09-01.

Для будущих аудитов GitHub Pages остаётся предложенным каналом, но новая публикация требует отдельного явного подтверждения. Неработающий сейчас custom domain `taskbot.pldata.io` не используется в целевом URL.

## Изменения в артефактах

- `report.json`: добавляются рассчитанные оценки, полнота данных, сгруппированные проблемы, структурированная статистика обхода и глубина проверки выдачи `checkedDepth`. Сырые факты и находки сохраняются.

- `execution-plan.md`: по-прежнему не создаётся до отдельного принятия отчёта пользователем.
- `mini-app/seo-reports/flowerlife-school/`: публичная копия принятого HTML, JSON и evidence для GitHub Pages.
- пользовательский skill `seo-report` и его runbook: менеджерская структура становится стандартом, а выбранный `language` определяет язык видимого отчёта.

## Проверка

Автоматические тесты должны подтвердить:

- порядок менеджерских блоков;
- отсутствие английских статических заголовков в русском отчёте;
- русское представление всех поддерживаемых статусов, приоритетов и кодов находок;
- невозможность прямого попадания английских `evidence`, `action` и provider message в открытую часть;
- отсутствие `Normalized evidence files`, `Executive top ten`, `Source coverage`, `Evidence`, `Action`, `n/a` и кодов находок в открытой части;
- корректный расчёт всех четырёх оценок и итогового балла;
- раздельный расчёт `collectionCoverage` и `scoringCoverage`, включая минимальную выборку;
- учёт URL, отброшенных лимитом обходчика, в завершённости обхода;
- нормализацию технического балла только по измеренной части без штрафа или подарочного балла за ошибку сбора;
- ограничение итогового балла при массовом `noindex`;
- отсутствие штрафа за недоступные данные владельца;
- группировку повторяющихся проблем;
- закрытое состояние технических разделов и карточек страниц;
- корректное экранирование URL и текстовых данных;
- сохранение подробного JSON и ссылок на исходные файлы.
- отсутствие секретов и `execution-plan.md` в публичном каталоге;
- HTTP 200 для опубликованного отчёта, JSON и всех относительных evidence-ссылок после успешного Pages workflow.

После тестов создаётся новый живой отчёт для `flowerlife-school.com`. Его проверяют на компьютере и экране шириной около 390 пикселей. До принятия обновлённого отчёта план выполнения не создаётся.

## Критерии приёмки

- Первый экран отвечает на вопрос о состоянии сайта без чтения технических таблиц.
- Первый экран содержит общий балл и статус либо явное состояние «Предварительная оценка» / «Недостаточно данных», четыре составляющие, полноту данных и главный вывод.
- Главные проблемы, позиции, видимость в ответах Алисы и скорость доступны без раскрытия технических блоков.
- Повторяющиеся проблемы сгруппированы.
- Подробности по страницам закрыты по умолчанию и раскрываются отдельно для каждого URL.
- Весь менеджерский текст Flowerlife написан на русском.
- В открытой части нет внутренних терминов и кодов проверок.
- Ограничения данных сформулированы коротко и честно.
- Техническая доказательная база не потеряна и доступна специалисту.
- Новый формат применяется будущей командой SEO-отчёта.

## Вне задачи

- Изменение самого сайта `flowerlife-school.com`.
- Подключение доступа к Яндекс.Вебмастеру или Google Search Console.
- Подмена выборочной проверки ответов Алисы официальной метрикой Яндекса.
- Создание плана внедрения до принятия обновлённого отчёта.
